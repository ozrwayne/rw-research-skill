# 多轮评审规则

审稿、辩论和复审共用这一套。回应别人的审稿意见时也照这套走。

## 一、两套模型换手

一方写的东西，由另一方审。Claude 写的稿交 Codex 审，Codex 写的稿交 Claude 审。

- 不走 API。两边各自打开本地评审目录，直接读台账和文件。
- 不靠转述。审的一方自己读稿子、读原始结果、读这一轮改了什么。
- 提示词里写死这一句：写的一方的说明不是证据，自己读文件；读改动本身，不读对改动的描述。
- 后期接中转站或用户自带 API 时，只换调用方式，规则不变。

## 二、对抗强度

不分档，直接用最高档：审的一方自己进目录读全部文件，写的一方无法决定它看到什么。

低强度档位在这套设计里没有意义，因为两边本来就共用一个目录。

## 三、评审记忆

审的一方在 `memory/<agent>-memory.md` 里记自己的怀疑，每轮追加，不删旧的：

- 这轮提了什么。
- 上轮哪些还没解决。
- 反复出现的模式。

每轮开新会话，第一件事是读这份记忆。作者没有正面回应的问题，不会因为换了一轮就消失，也不会因为上下文断了就被忘掉。

## 四、辩论

写的一方可以反驳，每轮最多三条。逼它挑最重要的争，不许逐条纠缠。

反驳格式，一条一份：

- 接受、部分接受还是不接受。
- 理由。
- 证据在哪：文件、位置、数字。

审的一方对每条反驳给一个裁决：

- 维持：反驳不成立。意见状态转 `sustained`，写清为什么不成立。
- 收窄：反驳部分成立。状态转 `narrowed`，写清收窄到什么范围。
- 撤回：反驳成立。状态转 `withdrawn`。

撤回有硬条件：必须写清是哪一份证据说服了它，并把这份来源连到这条意见上。说不出证据就不算撤回，只能是维持或收窄。台账脚本会挡住没有证据的撤回。

反驳一方不许编造证据、不许曲解结果。指出审的一方读错了代码或看错了指标，是合法反驳。

整轮辩论原样存进 `debate/round-N.md`，不做删节。

## 五、停机

两个条件同时满足才停：

1. 分数达到约定线。
2. 审的一方明确说可以了。

高分但审的一方说还不行，不停。轮数上限到了还没过，停下来列出剩下的问题和每个问题要花多少工夫，交给人判断继续还是换路子。

## 六、谁驱动修改，谁不判效果

改稿的模型不判自己改得好不好。Claude 改的稿由 Codex 判，反过来一样。

换不了手的时候，在复审结论里写明这一行：本轮验证与修改由同一方完成，可能只是改成了这个判断者喜欢的样子。

## 七、复审

作者改回来之后，对每条意见走三步：

1. 读作者声称改了什么。
2. 翻到它说的那个位置。
3. 自己核对改动和声称是不是一回事。

作者声明含糊的，例如“已按建议修改”，标成无法核实，不算已解决。

核完把每条意见的状态更新进台账，并写清下场。改动引入的新问题另立新意见，不塞进旧意见里。

## 八、存档

每轮评审的原始输出、辩论记录和裁决全部存进评审目录，挂进凭证链。

处置定下来时用 `record-credential` 生成评审凭据，记清是哪次讨论、谁确认、依据什么。撤回类的处置需要 Agent 共识、已委托权限或人类确认，建议级的凭据不算数。

## 九、不重跑

裁决类的检查只在稿子或数据变了之后重跑，不挂定时器。攻击、数字对账、引用核查都属于这一类：论文没变，重跑一遍不会有新信息。
